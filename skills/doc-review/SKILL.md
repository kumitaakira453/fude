# ドキュメントレビュー対応スキル

人間が fude で付けたレビューの指摘を読み取り、指摘に基づいてドキュメントを修正する。

## 引数

| 引数 | 必須 | 説明 |
| --- | --- | --- |
| 対象ファイルパス | いいえ | 修正対象の Markdown ファイル。省略時は直前に Write または Edit で作成・編集したファイルを対象とする |

## 前提

- `fude` に PATH が通っていること。通っていなければ次で張る

  ```bash
  mkdir -p ~/.local/bin
  ln -sfn "/Applications/fude.app/Contents/MacOS/app" ~/.local/bin/fude
  ```

- 人間が fude で対象ファイルに指摘を付けてあること

台帳はマシンに 1 つで、プロジェクトごとには分かれていない。`--project` でプロジェクトの
ルートを渡して絞り込む。`--file` は絶対パスでも相対パスでもよい。

## 手順

### 1. 指摘の取得

未対応の指摘を一覧する。

```bash
fude review list --project [プロジェクトルート] --file [対象ファイルパス]
```

既定は**未対応のみ**（最後の発言が自分でないもの）で、AI 向けの形式で出る。返信済みの
ものまで見直すなら `--status open`、解決済みも含めるなら `--status all`。件数が多いときは
`--brief` で 1 件 1 行の一覧にしてから絞る。人が読む詳しい形は `--format md`、機械的に
扱うなら `--format json`。

先頭の要約行（`未対応 n / 返信済み n / 解決済み n`）で全体の内訳が分かる。未対応が
0 件ならそこで終了し、要約をそのまま伝える。

### 2. 指摘の読み方

各指摘には、指摘した時点の本文（`本文:`）と、その箇所が**今どうなっているか**が
併記される。修正前にこの状態を必ず確認する。出力の `次:` の行に取るべき行動が
書かれているので、原則それに従う。

| 状態 | 意味 | 取るべき行動 |
| --- | --- | --- |
| 対象は書き換わっていない | 指摘された箇所が当時のまま残っている | そのまま修正する |
| 対象は書き換わった | 既に別の内容になっている | 併記される `現在:` を読み、指摘が今も当てはまるか判断してから直す |
| 対象は削除された | 該当箇所が無くなっている | 指摘が解消済みでないか確認する。解消済みなら修正せず返信だけ行う |
| 対象の位置が不明 | 本文が大きく変わり、対応する箇所を追えなかった | 引用文を手掛かりに自分で探す。見つからなければ推測で直さず、その旨を返信する |
| ファイルが無い | 移動・改名された | 修正せず、ユーザーに確認する |

修正は Edit ツールで最小限の変更にとどめる。

### 3. 返信

修正した各指摘に、何をしたかを返信する。

```bash
fude review reply --thread [指摘ID] --author AI --body "[修正内容の要約]"
```

指摘 ID は一覧の `#xxxxxxxx` の 8 桁。

**指摘を解決済みにしてはならない。`fude review resolve` を実行しない。** 修正が
意図どおりかを見て指摘を閉じられるのは、指摘した人間だけ。対応したものも、
対応しなかったものも、返信だけ残して未解決のままにする。

返信すると、その指摘は次回の一覧から外れる（未対応は「最後の発言が自分でないもの」で
判定する）。人間が同じ指摘に書き足せば、また未対応として出てくる。

### 4. 版の記録

そのファイルへの対応が一通り終わったら、現在の内容を版として記録する。次のレビューで
「どこが変わったか」を出すための基準になる。

```bash
fude review commit --file [対象ファイルパス] --message "[対応の要約]"
```

記録済みの版は `fude review versions --file [対象ファイルパス]` で新しい順に確認できる。

### 5. 再レビュー依頼

修正サマリーをユーザーに提示する。

```
## 修正サマリー

| 指摘 | 状態 | 対応 |
|------|------|------|
| #xxxxxxxx | [対象の状態] | [修正内容] |

すべて未解決のままにしてあります。fude で確認し、良ければそちらで解決してください。
```

修正しなかった指摘があれば、理由を添えて別の表に分けて示す。

## 注意事項

- **推測で直さない**: 対象の位置が不明な指摘は、引用文で探して見つからなければ
  返信で状況を伝える。それらしい箇所を当てずっぽうで書き換えない
- **解決済みにしない**: 対応の完了を宣言するのは版の記録（`review commit`）まで。
  指摘を閉じる判断は人間に残す。`review resolve` は理由があっても実行しない
- **版の記録は対応が終わってから**: 途中で記録すると、次のレビューの基準が中途半端になる
