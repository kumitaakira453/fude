# レビューの MCP サーバー

作成日: 2026-09-12 / 作成者: 汲田 晶

## 目的

CLI を残したまま、MCP の入口も出す。狙いは 3 つに限る。

- **ツール定義が最初から文脈に入る** — `--help` を引かなくても引数と意味が分かる。
  実測で `--help` の往復が 36 回あった
- **戻り値が構造化される** — テキストを読み取らず、型のあるオブジェクトで受け取る
- **権限・許可が楽になる** — Bash 呼び出しごとの判定を避け、作業が途中で止まらない

**位置解決の費用（実測 62%）はこれでは下がらない。** それはデータ設計の側の話で、
[指摘の位置解決](./指摘の位置解決.md)で別に扱う。MCP に期待するのは上の 3 つだけ。

## 現状で使えるもの

調べたところ、足場はほぼ揃っていた。

### 入口を足す形が既にある

`main.rs` は `run_cli_if_requested()` が真なら**ウィンドウを開かずに終わる**。
分岐は `argv[1] == "review"` の 1 か所だけ。ここに `"mcp"` を足せば同じ経路に乗る。

**新しい配布物は要らない。** `fude.app` のバイナリがそのまま MCP サーバーになる。
`~/.local/bin/fude` の symlink も既にある。

### 整形と中核が既に分かれている

`cli.rs` は `review::list()` / `reply()` / `resolve()` などを呼び、整形は
`format.rs` が持つ。MCP は同じ中核を呼び、整形を通さずに構造をそのまま返す。
**中核に手を入れる必要が無い。**

### 台帳の排他はプロセス間で効く

`store::update()` はロックファイルを `create_new` で取り、異常終了で取り残された
ロックは時間で無効とみなす。GUI・CLI・MCP が同時に書いても壊れない。

## 設計

### 置き場所

`fude mcp` サブコマンド。stdio で JSON-RPC を話し、クライアントが子プロセスとして
起動する。

### 常駐の重さと孤児の防ぎ方

stdio の MCP サーバーは、クライアントが子プロセスとして起動する。Claude Code の
セッションが増えれば、その数だけプロセスが立つ。

**メモリは問題にならない。** CLI モードの実測は最大 RSS 12.7MB、**専有は 4.4MB**。
RSS の大半はバイナリ（24MB）のマップ済みページで、これはファイル由来なので
全プロセスで共有される。5 セッション同時でも専有は 20〜25MB 程度にとどまる。
参考として、GUI の fude は 114.7MB。

**本当に気を付けるのは、親が死んだあとに残ることのほう。** 対策は 2 つ。

- **stdin が閉じたら即座に終わる。** クライアントが落ちればパイプが閉じる。
  そこで確実に抜ける。読み取りを待って永久に居座らせない
- **常駐を延ばす要素を持たない。** バックグラウンドのスレッド、ファイル監視、
  タイマーのいずれも置かない

### 共有デーモンは採らない

「1 本のデーモンを共有し、セッションごとには細い橋渡しだけを立てる」形を検討したが、
**stdio である以上、橋渡し自体がセッションごとに 1 プロセス要る**。プロセス数は減らず、
減るのはメモリだけになる。そのメモリが既に 4.4MB で問題になっていないので、
デーモンの寿命管理という複雑さを買うだけで終わる。

プロセス数を本当に無くせるのは、HTTP 転送に変えて常駐中の GUI が port を開ける形。
ただしそれは「GUI が起動していなくても動く」という `cli.rs` に明記された原則を崩す。
**将来の選択肢として残すにとどめ、今は採らない。**

### 状態を持たない

台帳をメモリに載せたままにしない。GUI と CLI が同じファイルを書き換えるので、
**呼び出しごとに読む**。読み込みは実測 2〜3ms で、持ち越して得られるものより
古い値を返す害のほうが大きい。

### ツールの並び

CLI のサブコマンドに 1 対 1 で対応させる。名前を変えると、CLI で分かっていることが
そのまま使えなくなる。

- `review_list` — 読み取り
- `review_reply` / `review_resolve` / `review_reopen` — 書き込み
- `review_commit` / `review_checkpoint` / `review_versions` — 版
- `review_gc` — 片付け

読み取り専用のものはその旨を宣言する。**許可を読み取りだけ先に通し、書き込みには
確認を残す**運用ができる。これが「権限が楽になる」の実体で、全部をまとめて
許すことではない。

### 一括返信を持たせる

CLI ではシェル関数で複数の指摘へまとめて返信していた。実測の区間では 16 件の返信を
12 回の呼び出しで捌いている。MCP は 1 ツール 1 呼び出しなので、素直に写すと往復が
増える。**複数の指摘へ一度に返信するツールを持たせる。**

### 戻り値

`--format json` が返すものと同じ構造にする。位置解決の設計で行範囲と確信度を足す
ことにしているので、それがそのまま MCP の戻り値にも乗る。**2 つの入口で別々の形を
作らない。**

### エラー

CLI は終了コードと標準エラーで返し、MCP は JSON-RPC のエラーで返す。中核が返す
`Result` を両方の形へ写すだけにして、文言を 2 か所で書かない。

## 実装の当たり

1. `run_cli_if_requested` の分岐に `mcp` を足す
2. stdio の JSON-RPC 受け口
3. ツール定義の宣言（一覧とスキーマ）
4. 各ツールを `review::*` へ配線
5. 一括返信

## 決めること

- Rust の MCP SDK を入れるか、JSON-RPC を手書きするか。プロトコル自体は単純なので、
  依存を増やす価値との兼ね合いで決める
- 対象を絞る引数（`--project` 相当）を、ツールの引数にするか起動時の設定にするか
- 書き込み系のうち、どこまでを読み取り専用の宣言から外すか

## やらないこと

- CLI の廃止。シェルでの手作業と、MCP を持たない場面での利用を残す
- 他の AI クライアントへの対応を前提にした設計。今は Claude Code だけを見る
- MCP で位置解決の費用を下げようとすること
